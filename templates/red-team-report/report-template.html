2. Attacker model

The attacker is not a particular profile — it is anyone. Most findings below can be exploited by anyone who can clone the repository, replay a stolen token, or point now-commonplace AI tooling at the code: no privileged position, no insider access, and no special skill is needed for the worst of them. The range runs from a random opportunist at the low end up to a privileged insider at the high end — but the exposure that matters is at the low end, and that is where this review holds the bar. A control that assumes either “this component is not compromised” or “nobody will find this” fails the design test.

Assumed adversary capabilities — from the lowest realistic bar upward
CapabilityMeaning
Low-skill / AI-assisted opportunistNo privileged position and little expertise. Uses off-the-shelf and AI tooling to scan a leaked or cloned repository, replay a stolen token, or hit an open endpoint. Enough, on its own, to exploit findings such as committed secrets, default/shipped accounts, and open endpoints.
Supply-chain maintainer / repo readerRogue developer, compromised vendor, or anyone with read access to the source repository — a direct path to production when secrets are committed.
Root access holderTotal control of one or more components — server, database, network segment, or codebase.
Collusion-capable & persistentCoordinates multiple compromised components; observes traffic, dumps memory, and runs campaigns over months.

Findings reachable at the lowest bar — a cloned repo, one leaked credential, one stolen token — are marked as such, because those need no foothold and no skill to hit today. Checking that controls also survive a privileged insider is added rigour, not the primary threat: the primary threat is that these are reachable by anyone.

4. Single points of compromise

Grouped by core — Governance, Identity, Access — worst gap first within each; adjacent config weaknesses that are not central points are listed separately.

Findings are ordered worst-first. Each is tagged with its OWASP Top 10:2025 category and primary CWE in its Standards & mappings row; the appendix severity table (§7.1) groups them by category. Each also names its single point of failure — the one artifact or party whose compromise defeats the control — and carries a documented precedent for the failure class, cited for its mechanism, never as a forecast of this organisation’s losses. Evidence is tagged Verified (observed in source) or Inferred (implied, not confirmed).

Access tokens are unbound bearer tokens — proof-of-possession is not enabled

High
F-01 · SG-03 · I-12 · T-05
Overview
Single point of failure: the access token. Possession is sufficient — any place the token passes through (browser memory, an XSS payload, a proxy or log, an uploaded support file) is a full-session takeover until it expires, replayable from any machine. Verified
Description
What the control is, why it is absent here, and what the attacker gains. State the mechanism in plain language a director can follow. State that an architectural artifact cannot be patched away — the liability exists as long as it does.
Proof of concept
Static-analysis evidence — no live exploit was run. Re-runnable from the repository root.
src/api/client.ts:17 config.headers.Authorization = `Bearer ${token}`; // no proof-of-possession header $ grep -rni "dpop|cnf|jkt" src/ # → no matches (server never checks)
Business impact
For an architectural / concentrated-trust finding, frame it as an inherent liability + historical breach + average cost — no vendor named. Example: Because the token is an unbound bearer credential, the application is inherently exposed to replay — this is not a bug to patch; the liability exists as long as possession alone grants access. It has played out in history (BP-KEY-05, CircleCI — a stolen token replayed remotely, every customer forced to rotate every secret). Breaches of this class cost, on average, USD $4.44M (IBM Cost of a Data Breach 2025). Put the average cost on EVERY finding (pick the sector figure); cite the breach for the mechanism, never its one-off total for the cost. For a coding/config finding, give the impact, a relatable breach if one fits, the average cost, and the real fix. Do not mention Tide/TideCloak in this report — that is the phase-2 companion.
